报告见 `seed17_audit/report.md`。全部数值来自真实记录，不是 miss 成本模拟。

利用一直存活的 background 请求每轮真实 token 时间点，按 batch 类型聚合主执行：

这些是批间真实时间区间，不是逐算子 profiler，不把差值都归因于某一个操作。
KV restore 从 14688 次、累计 8.477118 秒降为 474 次、0.272353 秒。
与此同时，单请求 decode 的专家命中从 9200 降为 260，实际 upload 从 11920 增为 20832。
四请求 decode 两组专家命中都是零，说明这一段可以通过调整 KV 空间获益而不额外损失专家命中；
单请求阶段则相反。两组均生成 248 tokens，但生成 token IDs 并不全部一致，按既定性能口径保留。

## 下一步选择，不改算法

另一条既有真实 trace：`results/qwen-20261015T011335Z-1993559b/expert_trace.jsonl`，
20-token prefill 的非空专家调用 2565 次、不同 `(layer,expert)` 2565 个，routed token 总数 7680。
对应 BF16 专家工作集 22.54 GiB，作为选容量窗口的依据，不冒充新执行器的路由实测。

新 entry `kite_burst_search.py` 固定最多两个实际场景，见 `docs/KITE_BURST_SEARCH.md`：
首场 32 GiB、15 次相同的真实 20-token 提示，加一条 512-token 实际初始请求，每请求输出 1 token。
历史若提出一半专家份额，baseline 容量 1820 专家，KITE 当前全 P 信号选择 2730 专家。
目标是让重复工作集处于两容量之间，测试历史首次刷新前的当前信号收益。
不锁定或修改基线提案；如果启动历史已经给出大容量，优势可能消失。

第二场 28 GiB、更短提示，只有首场整体加速未达 1.10× 才执行。
这是受控 prefill/首 token 突发，不是长生成或 decode-heavy 流量，不单独归因 fallback。
参数、四路径、真实执行器和每组启动标定口径不变；不新增精度探针或消融。
只有未来真实 GPU 跑完并审计，才能填写新场景的加速数字。
